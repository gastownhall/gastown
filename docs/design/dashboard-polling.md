# Dashboard polling and subprocess ownership

SSE reads the same fourteen-panel snapshot used to render the dashboard and expanded views. It checks every two seconds; the shared snapshot refreshes at most once per ten-second cache interval, even when no page request arrives. The snapshot includes every panel, canonical convoy IDs/totals, summary and explicit availability notices. Row order is canonicalized for hashing. Unrendered activity `Duration` is normalized; source timestamps, displayed ages and colors remain part of the hash. Command completion order and elapsed nanoseconds cannot create false updates.

This replaces the independent `gt status --json`, `gt hooks list` and `gt mail inbox` SSE probes. In the incident, status exceeded its three-second budget and owned 99 concurrent `bd` processes; requiring all three probes to succeed suppressed even the initial SSE update. A quick status response was not reliable either: contention on its detail lock can return runtime-only data. The dashboard now uses its existing panel reads directly.

One refresh is shared by HTML and SSE callers, including expanded panels. Waiters can disconnect promptly. The final departing waiter cancels an unfinished refresh; another active waiter keeps it alive. A new client cannot join an abandoned refresh: it waits for drain and retries within a bounded deadline, or receives an explicit HTTP 503 instead of a blank page. The configured fetch deadline (eight seconds by default) propagates into live `bd`, canonical convoy, GitHub and tmux command trees. At the deadline the handler publishes available results and explicit failed-panel notices without waiting for subprocess drain. The refresh reservation remains held until all fetchers exit, preventing a timed-out or non-context-aware fetch from overlapping its replacement.

A failed panel retains its last successful values and shows “Refresh failed; showing last known data.” Before its first successful fetch it shows “Unavailable; refresh will retry.” Raw CLI errors remain in server logs. These notices participate in the snapshot hash and HTML responses carry `X-Dashboard-State: degraded`, so an optional panel failure cannot silently erase data or starve the initial update. Repeated failures receive the same cache interval and stable hash. Recovery clears the notice and publishes the recovered data. Successful panels continue to update during other panels' failures.

Focused fixtures exercise the public SSE/handler path for initial delivery, changed data without page loads, unchanged-state stability, expanded-view coalescing, explicit failure/recovery and canonical last-good values. A context-ignoring fetcher verifies bounded waiters with no overlapping replacement, while a real live mail fetch against a fake `bd` process tree verifies deadline/disconnect cancellation. No production database is used.

This extends the polling coalescing in PR #4811. PR #4791 reduces redundant `mail read` mutations; it does not address the `mail inbox` fanout seen in incidents gt-8i2 and hq-wisp-nfmp6.

On Unix, dashboard subprocesses have a process-group cancellation hook and a bounded pipe wait. Synchronous read commands receive the internal `GT_MANAGED_READ=1` environment marker. Nested Gas Town command launchers then inherit the existing group instead of detaching. Without this inheritance, `gt mail inbox` can launch several detached `bd` processes which survive cancellation of the outer command and keep contending for the HQ schema initialization lock. Ordinary CLI commands retain their existing group policy. The marker is applied only to the explicitly classified dashboard reads, not mutation commands.

The CLI entry point supplies its own executable path to the dashboard API and canonical convoy reader. Library constructors retain an explicit path seam and never discover the test executable automatically. This prevents an adopted dashboard from silently executing an older installed `gt` whose nested subprocess behavior differs from the serving build.

Canonical convoy hydration, panel data, token protections, and the exact-origin/source readiness contract remain unchanged. Polling does not shorten the consumer's twelve-second acceptance deadline. Unix cancellation is exercised with the real mailbox fanout and fake `bd` executables; these tests require no live database. Windows keeps the existing process helper behavior and is not covered by the Unix process-group fixture.

The managed-read policy covers the actual Ready, Crew, Polecat, Mail Inbox, Status, Hooks, Rigs, and Convoy read calls. The Ready regression runs the real `/api/ready` handler and CLI `runReady`, including parallel town and rig `Beads.Ready` calls against fake executables. `mail read` is excluded because it marks delivery state; PR #4791 addresses its redundant mutations.

The browser bridges native EventSource `dashboard-update` messages to an ordinary HTMX DOM event of the same name. The `sse:` trigger prefix is reserved for HTMX-managed SSE sources and cannot be used for that bridge: it produces `htmx:noSSESourceError` and leaves the DOM stale despite a healthy stream. Refreshes select only `#dashboard-main` from the response before morphing. Swapping the full document re-executes bootstrap scripts and duplicates EventSource connections. A real Chrome fixture runs production HTML/JavaScript, native EventSource, HTMX and Idiomorph against mock data; it proves two automatic DOM updates without reload, stable unchanged state, one connection and canonical navigation after swaps.
